# Code & Documentation Deterministic Maintainability

**Document type:** Architecture / Proposal for Team Discussion  
**Date:** 2026-08-29  
**Purpose:** Deterministic maintainability checks for AI-agentic Python development

## 1. Executive Summary

The goal is to make Python projects maintainable when code is developed or modified by AI coding agents.

The central problem is synchronization between implementation, API/type information, documentation, examples, tests, and project rules.

The framework should deterministically detect:

1. **Non-availability** — required docstrings, type hints, arguments, returns, raises, etc. are missing.
2. **Drift in available information** — documentation/types/signatures exist but no longer agree with current code.
3. **Implementation drift** — function/class implementation changes while supporting documentation or other maintained representations are not appropriately reviewed or updated.

The proposed approach is **not to replace mature tools** such as Ruff, mypy/Pyright, pydoclint, and pytest. Use them as the foundation and add a small project-specific **Deterministic Synchronization Guard** for the remaining gap.

The custom layer should use Python's built-in `ast` module to extract independent components of each function/class and `hashlib` to generate deterministic fingerprints.

A function/class can therefore have multiple fingerprints:

- implementation/code fingerprint
- API/signature fingerprint
- type fingerprint
- documentation fingerprint
- exception/raise fingerprint
- example fingerprint, where applicable

The hashes do not need to be generated by Git. Python generates them. Git is used for version control and can trigger checks through pre-commit/CI.

## 2. Scope and Non-Goals

### In scope

- Python functions and classes selected by project policy.
- Public APIs and important internal APIs.
- Docstring availability and structure.
- Type annotation availability.
- Signature/documentation parity.
- Detecting implementation/API/documentation state changes.
- Machine-readable failures suitable for AI coding agents.
- Integration with pytest, pre-commit, CI, and existing architecture/CKG checks.

### Not in scope

The system should not attempt to mathematically prove that natural-language documentation is semantically correct.

A hash can prove that a representation changed or did not change. It cannot prove that a sentence such as "retries three times" is semantically correct.

Semantic validation should remain the responsibility of tests, explicit rules, and—where useful—AI-assisted review.

## 3. Design Principles

### 3.1 Reuse mature tools

Do not create custom versions of existing capabilities.

Use:

- **Ruff** — linting and documentation/style rules.
- **mypy or Pyright** — static type checking.
- **pydoclint** — docstring/signature parity.
- **pytest** — behavioral tests and project guards.
- **pytest doctest** — executable documentation examples where valuable.
- **Git/pre-commit/CI** — versioning and execution gates.
- Existing **CKG / dependency analysis** — change impact.

### 3.2 Keep custom logic small

The custom framework should primarily answer:

> "What maintained representation changed, and what related representation did not?"

It should not become a second general-purpose Python linter.

### 3.3 Deterministic first

For the core synchronization signal, identical normalized input must produce identical fingerprints.

### 3.4 Fail with actionable information

A failure must tell the AI agent:

- symbol name
- file and line
- what changed
- old fingerprint
- new fingerprint
- related representation that did not change
- expected action

### 3.5 Baseline changes must never silently self-approve

The framework must not automatically update its baseline merely because source code changed.

A new synchronized state should be recorded only after the validation workflow succeeds.

## 6. Multiple Fingerprints Per Function/Class

A single function/class can legitimately have multiple hashes because the AST provides a structured representation of the same symbol.

Example:

```python
def calculate_total(price: float, tax: float) -> float:
    """Calculate the total price including tax.

    Args:
        price: Base price.
        tax: Tax amount.

    Returns:
        Total price.
    """
    if tax < 0:
        raise ValueError("tax cannot be negative")

    return price + tax
```

Conceptually:

```text
calculate_total
|
+-- CODE_HASH
|     normalized implementation AST
|
+-- API_HASH
|     parameters + defaults + signature structure
|
+-- TYPE_HASH
|     parameter annotations + return annotation
|
+-- DOC_HASH
|     normalized docstring
|
+-- RAISE_HASH
|     normalized exception behavior
|
+-- EXAMPLE_HASH
      documented executable examples, if applicable
```

These hashes are independent even though all components belong to the same FunctionDef AST node.

## 7. What Each Fingerprint Means

### 7.1 CODE_HASH

Represents implementation logic.

It should be calculated from a normalized AST representation of the implementation body.

The normalization should exclude irrelevant changes such as:

- whitespace
- formatting
- comments
- source locations
- the docstring itself

This avoids treating a comment-only change as an implementation change.

### 7.2 API_HASH

Represents the callable/class interface.

Potential inputs:

- parameter names
- parameter ordering
- positional/keyword structure
- defaults
- varargs/kwargs

### 7.3 TYPE_HASH

Represents type annotations:

- parameter annotations
- return annotation
- relevant class attribute annotations

Keeping it separate initially gives better diagnostics.

### 7.4 DOC_HASH

Represents normalized documentation.

For functions, this can include:

- summary
- Args
- Returns
- Raises
- examples

It may be useful to hash sections independently in a later version.

### 7.5 RAISE_HASH

Represents detectable exception behavior from AST.

For example:

```python
raise ValueError(...)
```

If a new exception type is introduced, the fingerprint changes and the documentation audit can be triggered.

This is a project-specific signal, not a guarantee that every possible runtime exception has been detected.

### 7.6 EXAMPLE_HASH

Optional.

Use only where executable/documented examples are part of the project's maintenance contract.

## 8. Baseline / Synchronization State

A synchronization state can initially be stored in a version-controlled file such as:

```text
.project/
    pydocsync/
        fingerprints.json
```

Example:

```json
{
  "mypackage.parser.parse_config": {
    "code": "8f4a...",
    "api": "92bc...",
    "types": "6c11...",
    "doc": "71de...",
    "raises": "ab92..."
  }
}
```

The baseline is a **known synchronized state**, not merely a cache.

It should be committed together with the corresponding source/documentation.

## 9. Who Calculates and Observes the Hashes?

### Hash generation

Python code in the custom guard calculates the fingerprints using:

```text
ast
hashlib
```

Git does not calculate these fingerprints.

### Observation

The synchronization guard observes changes when invoked by:

1. the AI agent's validation command,
2. pre-commit,
3. CI,
4. normal developer test execution.

Recommended command:

```bash
pytest tests/guards/test_doc_sync.py
```

or:

```bash
pytest tests/guards/
```

### Git's role

Git provides:

- version history
- source/documentation versioning
- commit/PR boundaries
- pre-commit/CI integration

Git is not the hashing engine.

## 10. Example: Implementation Changed but Docstring Did Not

Baseline:

```text
calculate_total

CODE    = AAA111
API     = BBB222
TYPES   = CCC333
DOC     = DDD444
RAISES  = EEE555
```

AI changes implementation to add:

```python
if tax < 0:
    raise ValueError("tax cannot be negative")
```

New state:

```text
CODE    = XXX999    changed
API     = BBB222    unchanged
TYPES   = CCC333    unchanged
DOC     = DDD444    unchanged
RAISES  = ZZZ888    changed
```

Guard result:

```text
FAIL: calculate_total

Implementation changed.
Exception behavior changed.
Documentation fingerprint is unchanged.

Action:
Review and update the function documentation.
Run the documentation/type/behavior validation again.
```

This is the core AI-maintainability signal.

## 11. Important: Hash Mismatch Is a Review Trigger, Not Semantic Proof

A code hash changing does not automatically mean the docstring is wrong.

Example:

```python
total = price + tax
```

changed to:

```python
total = sum((price, tax))
```

The implementation fingerprint changes, but externally documented behavior may remain identical.

Therefore:

```text
CODE changed
+
DOC unchanged
```

should normally mean:

> **Documentation review required**

rather than:

> **Documentation is definitely incorrect**

This distinction prevents excessive false positives.

## 12. Handling Intentional Changes

A mechanism is needed for cases where code changes but documentation correctly remains unchanged.

Possible design:

```text
pypydocsync accept --symbol mypackage.foo
```

or a commit/PR marker such as:

```text
PYDOCSYNC-REVIEWED: mypackage.foo
```

The exact mechanism should be decided after a prototype.

The important principle is:

> **Intentional exceptions must be explicit and auditable, never silent.**

## 13. Three Failure Modes

### Problem 1 — Non-availability

Examples:

- missing docstring
- missing type annotation
- missing Args
- missing Returns
- missing Raises where required

Detection:

```text
Ruff
mypy/Pyright
pydoclint
custom AST guard
```

Result:

```text
FAIL
Required documentation/type information is missing.
```

### Problem 2 — Drift in available information

Example:

```python
def foo(a: int, b: str) -> bool:
```

but documentation describes different parameters.

Detection:

```text
pydoclint
AST guard
type checker
```

Result:

```text
FAIL
Documentation does not match current callable contract.
```

### Problem 3 — Implementation drift

Examples:

```text
CODE_HASH changed
API_HASH unchanged
DOC_HASH unchanged
```

or:

```text
RAISE_HASH changed
DOC_HASH unchanged
```

Detection:

```text
custom synchronization guard
```

Result:

```text
FAIL / REVIEW REQUIRED
Implementation-related representation changed
without corresponding documentation-state change.
```

## 14. Classes

The same approach can apply to classes.

A class fingerprint can contain:

```text
Class
|
+-- CLASS_API_HASH
+-- CLASS_DOC_HASH
+-- BASE_CLASSES_HASH
+-- ATTRIBUTES_HASH
+-- METHOD_SUMMARY_HASH
+-- METHOD_LEVEL_FINGERPRINTS
```

However, class handling should be introduced after functions are working reliably.

A class can contain many independently maintainable methods, so blindly hashing the entire class can create unnecessary noise.

Recommended design:

> **Treat the class as a container and maintain individual method/function fingerprints inside it.**

## 15. Module-Level Documentation

Modules can also be tracked:

```text
module
|
+-- module_doc_hash
+-- public_symbols_hash
+-- imports/architecture fingerprint
```

But this should be a later phase.

Start with functions/classes that have the highest maintainability value.

## 16. Recommended Implementation Phases

### Phase 1 — Existing tooling baseline

Implement and stabilize:

```text
Ruff
mypy/Pyright
pydoclint
pytest
doctest where appropriate
```

Do not build custom hashing yet.

### Phase 2 — AST inventory

Build a read-only scanner that reports:

```text
file
symbol
type
line
docstring present?
annotations present?
parameters
returns
raises
```

No enforcement initially.

### Phase 3 — Fingerprinting prototype

For selected functions, generate:

```text
code_hash
api_hash
type_hash
doc_hash
raises_hash
```

Compare against a baseline.

### Phase 4 — pytest synchronization guard

Make mismatches deterministic pytest failures.

### Phase 5 — AI-agent integration

Produce highly actionable failures.

Example:

```text
PYPYDOCSYNC001:
symbol: parser.parse_config
code: CHANGED
api: UNCHANGED
types: UNCHANGED
doc: UNCHANGED
raises: CHANGED

Required action:
Review documentation for implementation/exception changes.
```

### Phase 6 — Git/pre-commit/CI

Run the guard automatically.

### Phase 7 — CKG integration

Use the existing CKG to determine affected callers/callees and prioritize documentation review when an API/behavior change has a larger blast radius.

## 18. AI-Agent Feedback Contract

The guard should be deliberately designed for AI consumption.

Bad:

```text
FAILED test_doc_sync
```

Good:

```text
PYPYDOCSYNC001

Symbol:
    mypackage.parser.parse_config

Detected:
    CODE_HASH changed
    RAISES_HASH changed

Not changed:
    DOC_HASH

Likely issue:
    Implementation/exception behavior changed while
    documentation remained unchanged.

Required action:
    Review the docstring and update it if the new behavior
    is externally relevant.

Do not update the baseline until validation passes.
```

This turns the test suite into an **agent governance mechanism**.

## 19. What This Framework Can Guarantee

It can deterministically guarantee:

- required information exists, according to configured rules;
- signatures and documented parameters can be checked for parity;
- type annotations can be statically checked;
- known AST-level implementation changes can be fingerprinted;
- documentation changes can be fingerprinted;
- synchronization-state changes can be detected;
- executable examples can be tested;
- project-specific rules can be enforced;
- failures can be produced consistently for AI agents.

## 20. What It Cannot Guarantee

It cannot prove that natural-language documentation is semantically perfect.

For example:

```text
"Processes the file using an optimized algorithm."
```

No ordinary hash can determine whether the algorithm is actually "optimized."

Likewise, runtime behavior hidden behind:

- reflection
- decorators
- dynamic dispatch
- external services
- configuration
- environment variables
- metaprogramming

may not be fully represented by a static AST fingerprint.

Therefore the framework must remain a **deterministic verification and review-trigger system**, not a claim of complete semantic proof.

## 22. Recommendation to the Team

Do **not** approve a large custom framework immediately.

Approve a **small proof of concept** with this objective:

> For 20–50 representative Python functions, deterministically detect missing documentation/type information, signature/documentation drift, and implementation changes that occur without a corresponding documentation review.

The proof of concept should measure:

1. false positives;
2. false negatives;
3. runtime;
4. baseline maintenance effort;
5. quality of AI-agent feedback;
6. compatibility with Git/pre-commit/CI;
7. usefulness of CKG impact information.

Only after this experiment should the project decide whether to expand the fingerprint model.

## 23. Proposed Team Decision

The proposed direction is:

> **Use established Python quality/type/documentation tools for problems they already solve, and build only a thin AST-based deterministic synchronization layer for the remaining code-to-documentation drift problem.**

The custom layer is not intended to compete with Ruff, mypy, pydoclint, pytest, or documentation generators.

Its unique responsibility is:

> **Detect that a maintained representation of a Python symbol changed without the corresponding synchronized representation being reviewed/updated, and provide an actionable deterministic signal to the AI coding agent.**

This provides a practical foundation for AI-agentic Python development while minimizing custom infrastructure.
